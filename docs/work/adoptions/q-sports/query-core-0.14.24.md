# Adopt @ttt-productions/query-core 0.14.24

**What:** New session-aware mutation owner; `createCallables` moves here; batch reads hold their answer through a failure.
**Severity:** high
**Came from:** the ttt-packages shared-standards run (Phase 3 package batch)

- **Package and version:** `@ttt-productions/query-core` 0.14.24.
- **Release:** `./scripts/release-multiple.sh dev-standards firebase-helpers repo-guards query-core chat-schemas report-core notification-core ttt-core upload-ui chat-core chat-react patch`.
- **What changed:** New in `./react`: `MutationSessionProvider({ currentUid })`; `useSessionMutation` (returns TanStack's result; `mutationFn(variables, context)` receives `context.session = { uid, isCurrent(), assertCurrent() }`; an action whose session ended skips every callback, rejects `mutateAsync` with `MutationSessionEndedError` — `name 'AbortError'`; its `cause` is the failure when the answer was a failure, and it has no `cause` when a success landed after the session ended (the write may have committed) — and never starts a queued, paused, or restored run; with no provider the session is always current); and `createCallables` with its types, moved from firebase-helpers, where every callable kind is fenced by the same session, the policy's failure toast included. `useFirestoreSet/Update/Delete/Batch` run on the owner. `useBatchFirestoreDocs`: an answered id stays `present` (with `failure?: { error, retrying }`) and stays in `data` through every failure except `permission-denied`, in one-shot and subscribe mode. The react-query peer floor is `>=5.90.0`.
- **What the app must change:** Install `@ttt-productions/query-core@latest` wherever it is declared. Mount `<MutationSessionProvider currentUid={...}>` inside the QueryClientProvider with the signed-in uid. Import `createCallables` from `@ttt-productions/query-core/react`. Replace every raw `useMutation` with `useSessionMutation`; a multi-step `mutationFn` calls `context.session.assertCurrent()` between its awaits. At `mutateAsync` call sites and in the MutationCache monitoring adapter, treat `MutationSessionEndedError` as the ended session's action: the current session does nothing with it, and monitoring reads its `cause` when there is one (a late success has none, and its write may have committed). A batch consumer renders a `present` outcome that carries `failure` as an answered read with an inline failure.
- **Done when:** The lockfiles name `@ttt-productions/query-core` 0.14.24 or later, no raw `useMutation` remains and repo-guards' `mutationOwner` is green, and the gate is green.
